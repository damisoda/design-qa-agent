# 동일 Figma·로컬 프런트의 속도 비교

2026-10-21. Atelier Discover 글자 넘침 통제 사례를 같은 로컬 환경에서 개선 전 3회, 개선 후 3회 실행했습니다. 각 실행은 **Dify 검사 → Dify 수정 시작 → Gemma의 파일 읽기·코드 수정 → 브라우저 재검증** 경로를 거쳤습니다.

## 측정 결과

| 단계 | 개선 전 중앙값 | 개선 후 중앙값 |
|---|---:|---:|
| Dify 검사 | 51.7초 | 38.9초 |
| Dify 수정·재검증 | 92.5초 | 60.7초 |
| 전체 | 143.8초 | 98.8초 |

전체 중앙값은 **31.3% 감소**했습니다. 단계별 중앙값의 합은 전체 중앙값과 다를 수 있습니다. 시간은 녹화 재생속도가 아니라 Dify 파이프라인의 실제 시작·완료 시각 차이입니다.

| 조건 | 1회 | 2회 | 3회 |
|---|---:|---:|---:|
| 개선 전 | 145.8초 | 140.0초 | 143.8초 |
| 개선 후 | 98.3초 | 98.8초 | 102.8초 |

## 결과가 같았는지

- 입력 프런트 파일과 Figma 내보내기 JSON의 해시가 동일합니다.
- 결함 ID, 크기별 px, 해결한 결함 목록을 대조했습니다. 모든 실행에서 같은 결함 보고 2건이 해결됐고 새 결함은 0건이었습니다.
- 최종 수정 CSS의 파일 해시도 여섯 실행 모두 동일합니다.
- 375×812, 390×844, 430×932, 375×667, 320×568의 전후 캡처 5쌍을 확인했습니다.
- 버튼 검사는 375×812, 320×568, 430×932에서 유지됐습니다. Figma 글자 노드 10개 대응도 유지됐습니다.
- 원본은 수정하지 않았습니다. 모델이 만든 변경은 사본에서만 검증했습니다.
- 여섯 실행의 검사·수정 Dify 워크플로 12개가 모두 성공했습니다.

## 바꾼 부분

1. 모델 사전 확인, 기준 화면 검증, 모델 호출, 후보 빌드·측정 시간을 별도로 기록합니다. Ollama가 반환한 로드·입력 처리·생성 시간도 보관합니다.
2. 기존 브라우저와 정적 서버를 공유하면서 독립된 컨텍스트의 시안·버튼 검사를 최대 3개씩 병렬 실행합니다. 결과는 원래 입력 순서대로 모읍니다.
3. 모델 프롬프트에 반복해서 넣던 코드 덩어리를 줄이고 후보 파일·줄 위치를 제공합니다. 모델이 도구로 파일을 읽어야 편집할 수 있다는 제한은 유지합니다.
4. 넘침 수정은 가장 크게 넘쳤던 크기부터 확인합니다. 여전히 실패하면 전체 검증을 기다리지 않고 수정 루프로 돌려보냅니다. 여기서 통과해도 전체 검증은 필요합니다.
5. 같은 수정 실행 안에서 정적 사본의 코드와 검사 조건이 같고 전체 검증이 이미 통과했다면, 그 결과를 최종 묶음 검증에 사용합니다. 다른 코드·조건, 빌드가 필요한 앱, 외부 심볼릭 링크, node_modules가 있는 사본에는 이 재사용을 적용하지 않습니다. 누락·회귀·사용자 흐름 실패가 있는 결과도 재사용하지 않습니다.

모델 호출은 개선 전 `read → edit`, 개선 후 `read → read → edit`였습니다. **호출 횟수가 줄었다는 결과는 아닙니다.** 이번 사례의 시간 감소는 병렬 검사와 동일 정적 사본의 중복 검증 제거가 중심이며, 실패 후보의 조기 중단 효과는 이 성공 사례만으로 측정하지 않았습니다.

## 검증과 범위

전체 자동 테스트 **162개 통과, 실패 0개**. 실제 Chrome에서 직렬·병렬 결과와 클릭 검사 범위를 비교하고, 소스 변경·회귀·누락·실패한 흐름이 있는 결과의 재사용을 거부하는 테스트를 포함합니다. Dify를 사용할 수 없을 때 로컬 수정을 우회 실행하지 않는 테스트도 통과했습니다.

한 통제 사례의 반복 결과입니다. 미사용 서비스나 여러 화면 앱에서도 31% 빨라진다는 의미는 아닙니다. 전후를 순서대로 측정했으며 실행 순서를 무작위로 섞은 실험은 아닙니다. 모델은 매 실행 후 기존 정책대로 내려 메모리 보호 정책을 유지했습니다.
