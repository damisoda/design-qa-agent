# dqa — 디자인-구현 결함 검수 도구(로컬)

화면을 여러 크기로 실제로 열어 재고, 변경 전과 비교해 새로 생긴 결함을 찾고, 원인 코드를 짚고, 고치는 패치까지 검증해 준다. 측정 결과와 팀 코드는 이 컴퓨터와 맥미니(로컬 모델) 밖으로 나가지 않는다.

## 빠른 시작

```bash
cd dqa
npm install                        # playwright-core 1개(크롬은 Playwright 캐시의 chromium을 찾아 쓴다)
node cli.js doctor                 # 준비 상태 점검(크롬, 맥미니 터널, 모델, 메모리, gh, 빌드)
node cli.js up                     # 맥미니 터널 열기(LLM 해석을 쓸 때만)
node cli.js serve                  # 웹 화면 http://127.0.0.1:8792
```

명령 한 줄로 검사:

```bash
# 로컬 작업 폴더(바이브코딩 중인 프로젝트): 커밋 전(HEAD)과 비교해 새로 생긴 결함만 따로 센다. 폴더는 읽기만 한다
node cli.js check --local ~/my-app                    # 비교 없이: --base none, 다른 커밋과: --base <ref>
node cli.js fix --run <실행 ID>                         # 사본에서 수정·빌드·재측정으로 검증
node cli.js apply --run <실행 ID> --confirm "적용"       # 검증된 수정을 작업 폴더에 넣는다(없으면 미리보기만)
node cli.js apply --run <실행 ID> --undo --confirm "되돌리기"
# 빌드 비교: 결함 전(PR #221 병합 전)을 수정 후와 비교 → 새로 생긴 결함 3건, 종료 코드 1
node cli.js check --dist cbh-221-pre --base-dist cbh-221-post --recipe cbh/report
# 실행 중인 아무 웹앱(로컬 주소만)
node cli.js check --url http://127.0.0.1:3000/ --recipe local/home --src ~/my-app   # 첫 화면만. 다른 화면은 레시피를 만든다
# 저장소 브랜치·PR 검사(독립 클론 ~/design-qa-cases/cbh-gh, 커밋별 빌드 캐시)
node cli.js check --repo cbh --ref develop
node cli.js check --repo cbh --pr 221
# 코드 에이전트: 문제 정의서를 받아 수정 → 평가용 사본에 적용·빌드·재측정으로 검증
node cli.js fix --run <실행 ID>
# PR 준비(로컬 브랜치·커밋·타입 검사·PR 본문). 올리기는 확인 문구가 있어야 하고 항상 초안
node cli.js pr --run <실행 ID> [--onto develop]
node cli.js pr --run <실행 ID> --push --confirm "PR 올리기"
# Figma 시안과 값 비교: 플러그인(../figma-plugin)으로 보낸 시안 이름이나 design.json 폴더. 화면이 여럿이면 "화면=시안,…"
node cli.js design list
node cli.js design pull --url "https://www.figma.com/design/<파일>/…?node-id=12-34"   # REST, 토큰은 환경 변수 FIGMA_TOKEN만
node cli.js check --local ~/my-app --design <시안 이름> --interact                   # --interact: 버튼·링크를 눌러 반응 없음·오류·빈 화면
node design/render.js <design.json>                                                   # 시안 그림이 없을 때 값으로 그림 만들기
# 안전영역(노치·홈 인디케이터) 흉내, 첫 화면 한 장만 재기
node cli.js check --dist <빌드> --recipe cbh/guardian_home --widths notch3        # 또는 --safe 47,34
node cli.js check --dist <빌드> --recipe cbh/report --widths 375x812 --scroll none
# 측정 규칙 단위 시험
node --test test/
```

## 로컬 모드

- 폴더 종류를 알아서 정한다: Expo(`expo export --platform web`), Vite(`vite build`), CRA(`react-scripts build`), 정적 사이트(index.html만). 다르면 폴더에 `.dqa.json`을 둔다.

```json
{ "build": ["vite", "build", "--outDir", "{out}"], "src_dir": "src", "env": {}, "recipes": ["local/home"], "widths": "mobile5", "stubs": null }
```

- 작업 폴더를 APFS 복제(`cp -c`)로 떠서 `~/design-qa-cases/local/` 사본에서 빌드한다. 비교 기준(HEAD)은 `git archive`로 꺼내고, lock 파일이 같으면 작업 폴더의 node_modules를 복제해 쓴다(다르면 `--allow-install` 승인 필요).
- 작업 폴더에 쓰는 것은 `apply --confirm "적용"`뿐이다. 검사한 뒤 고칠 파일이 바뀌었으면(내용 해시가 다르면) 적용하지 않는다. 원래 파일은 실행 폴더 `fix/backup/`에 남기고 `--undo --confirm "되돌리기"`로 되돌린다.
- 웹 화면: 새 검사에서 "작업 폴더"를 고르고, 수정 화면의 "작업 폴더에 적용"에 확인 문구를 넣는다.

## 지키는 것

- 원본 소스와 사용자 작업본(`~/Come-back-home`)에는 쓰지 않는다. 그 경로는 코드에서 거부한다. 수정 검증은 `~/design-qa-cases/fix/` 사본에서만 하고 끝나면 지운다.
- 기본 검사는 모바일 5개 크기(375×812, 390×844, 430×932, 375×667, 320×568)다. CLI·웹·Dify에 같은 기본값을 쓴다. 다른 프로필은 명시적으로 선택한다.
- 모든 검사 단계에서 POST·PUT·PATCH·DELETE 등 쓰기 요청은 가짜 응답으로 처리한다(`write_requests.jsonl`). 출처는 스킴·호스트·포트가 정확히 일치할 때만 허용한다(레시피 allow_hosts 포함). WebSocket은 검사 중 모두 막고 `blocked_requests.jsonl`에 남긴다.
- 한 크기·시안·상호작용 검사라도 실패하면 상태 incomplete·종료 코드 2로 보고하며, 변경 전과의 새로 생김·해결 판정과 수정 시작을 보류한다.
- 적용·PR 준비는 묶음의 빌드와 모든 재측정이 성공하고, 대상 결함이 해결되고, 회귀가 없을 때만 가능하다.
- LLM은 맥미니 로컬 모델만 쓴다. 다른 모델이 올라가 있거나 여유 메모리가 20% 미만이면 부르지 않고, 끝나면 내린다. 이미지는 보내지 않는다.
- GitHub에는 확인 문구가 있을 때만 쓴다(push + 초안 PR). 브랜치·커밋은 독립 클론 안에서만 만들고, 병합은 하지 않는다.
- 웹 화면은 127.0.0.1에서만 열리고, 브라우저 요청은 `X-DQA` 머리글이 있어야 받는다.

## 새 화면·새 앱 추가

1. `recipes/<앱>/<화면>.json`을 만든다(예: `recipes/cbh/report.json`). 단계는 `click`·`fill`·`wait_text`·`if_visible`·`use`.
   - 백엔드 없이 띄워야 하면 `"stubs": "stubs.json"`으로 API 응답 대역을 준다(`{ "stubs": [{ "method": "POST", "path": "/auth/signup", "json": {...} }] }`). 경로 끝이 맞거나 `re`에 맞는 요청을 브라우저 안에서 받는다. `"$body.키|기본값"`은 요청 본문 값으로 바뀐다.
2. `node cli.js recipe test --dist <빌드> --recipe <id> --size 375x812`로 들어가지는지 확인한다. 실패하면 그때 보이는 글자와 캡처를 보여 준다.
3. 빌드 이름은 `config/default.json`의 `dists`, 저장소 빌드 설정은 `config/repos.json`.

## Dify 앱

- `dqa · 검사→문제 정의→수정→PR`(v5, 10-12): 작업(검사·상태·수정 시작·적용·되돌리기·PR 준비·PR 올리기·시안 목록)을 사람이 고르면 `dqa_act` 도구가 한다.
  - 검사·상태이고 새 결함이 있으면 Dify 안에서 보고서 에이전트가 돈다.
    - 순서: `dqa_facts`(측정 사실) → `dqa_llm_ready`(맥미니 여유 20%·모델 하나·중계기) → 3주차 검색어 확장 → 문서 검색(design-qa-docs-v2) → 사례 검색(design-qa-cases-v2) → 근거 정리 → 근거 짝짓기(결함별) → LLM 노드(gemma4:e4b-16k-nothink) → `dqa_judge`
    - `dqa_judge`는 숫자·근거 ID를 측정 사실과 검색 근거로 검증하고, 통과한 것만 결함 기록에 저장한 뒤 모델을 내린다.
  - 결과는 ECharts 차트(규칙별·검사 종류), 결함 캡처, 시안·구현 값 표, 정의서로 보인다.
    - 근거는 "모델 인용"과 "3주차 검색 자동 연결"을 나눠 적는다.
    - 맥미니를 부를 수 없으면 LLM 단계만 건너뛴다.
  - 생각 끔 중계기(`ops/nothink_proxy.py`)는 `dqa up`이 터널과 함께 띄운다. 검사는 작업 폴더·시안 이름·눌러 보기를 받는다. 실행 ID를 비우면 웹 화면·Dify에서 시작한 가장 최근 검사(적용·되돌리기는 작업 폴더 검사)를 쓴다. 결과에 시안 비교 요약과 수정 요청문이 나온다. 작업 순서는 LLM이 정하지 않는다. 수정은 몇 분 걸려 시작만 하고 "상태"로 확인한다(Dify API 도구 제한 60초). PR 올리기는 확인 문구 입력란에 "PR 올리기"를 넣어야 한다.
- `dqa · 디자인 검수(로컬 도구 호출)`: 빌드·화면을 고르면 `dqa_check`가 검사 요약을 돌려준다.
- 만들기: `dify/dify.py register` → `dify.py dsl-act <provider_id>`(그래프는 `dify/act_v5.py`) → `../dify_import.py dify/dqa-act.dsl.yml --app <작업 앱 id>`. 스튜디오 편집 화면을 열어 둔 채 가져오면 자동 저장이 초안을 되돌릴 수 있으니 닫고 한다.

## 아직 없는 것

- main(10-09)처럼 lock이 바뀐 커밋은 npm ci(다운로드)가 필요하다. `--allow-install`을 줄 때만 받는다.
- 상태(눌림·포커스·비활성)·키보드 검사. 시안의 변형(variant)·상태 프레임 비교.
- 아이콘(벡터) 노드 짝짓기, Tailwind 클래스 수정(제안 CSS는 요청문으로만), React Native 스타일 객체의 시안 값 수정.
- 눌러 보기 결함의 자동 수정 검증(다시 눌러 확인)은 아직 없다. 수정 요청문으로 고친다.
- Figma REST 가져오기는 모의 응답 시험만 확인했다. 실제 Figma 데스크톱 플러그인 가져오기는 검증했다.


### 웹 검사와 진행 상태

웹의 새 검사는 작업 폴더와 Figma 시안을 먼저 고른다. 비교 기준·화면·크기·설명·수정 검증은 추가 설정에서 바꾼다. Figma 앱에서 시안 선택을 누르고 실제 파일에서 dqa 플러그인을 실행한 뒤 프레임을 가져온다. 최근 가져온 시안도 다시 선택할 수 있다.

웹 검사 버튼 → 게시된 로컬 Dify 워크플로 → dqa 준비·측정·시안 비교·눌러 보기 → Dify 근거 검색·Gemma 문제 설명 → 숫자·근거 검증 순서로 실행한다. 설명 생성을 꺼도 Dify를 거친다. `config/default.json`의 `dify.app_id`가 게시된 작업 앱을 가리켜야 하며, 현재 연결은 `docker-api-1`에서 기존 서비스 호출 방식으로 실행한다. Dify를 사용할 수 없으면 직접 로컬 모델로 우회하지 않는다.

진행 화면은 실제 크기별 상태·완료 개수, 최근 측정 캡처, 먼저 발견된 항목을 보여 준다. 초기 항목은 최종 묶기·재측정·변경 비교에서 달라질 수 있다. 근거 검색·설명 요청·설명 검증은 Dify의 실제 노드 이벤트를 사용한다. 모델 요청 중 `/api/ps`로 실제 적재 여부를 확인하며, 전체 진행률이나 남은 시간을 임의로 계산하지 않는다. 요소 검사 화면은 실제 Chrome의 규칙 순회와 시안 비교·클릭 검사에서 발생한 이벤트만 표시한다. 구현과 대응 Figma 요소는 색 채움 없이 검은 테두리와 같은 번호로 표시하고 측정값·발견 근거를 나란히 보여 준다. 빠른 이벤트는 화면 갱신 사이에 여러 개가 완료될 수 있으며, 검사를 느리게 하거나 가짜 요소 순회를 재생하지 않는다. 검사 뒤에도 요소 목록에서 기록을 선택할 수 있다.

중지하면 측정·빌드 자식 프로세스를 종료하고 Dify에 중지를 요청한다. 완료한 측정은 유지하며, 만료된 요청의 늦은 설명 저장은 거부한다. 설명 연결 실패 시 결과 화면에서 **Dify에서 설명 다시 요청**으로 재측정 없이 설명만 다시 실행할 수 있다. 실제 검증: `eval/ux-progress-20261014/README.md`.

### 실제 Figma 앱과 요소별 검사

macOS의 Figma 데스크톱 앱을 열어 파일이나 `.fig`를 선택할 수 있다. 플러그인은 현재 파일명·페이지·선택 프레임을 로컬 서버에 전달하고, 웹에서 선택한 프레임의 실제 노드 값과 PNG를 요청한다. 프레임 링크는 Figma 앱을 여는 데 사용하며, 일반 개발 플러그인에서 파일 키가 제공되지 않으면 링크 일치를 확인했다고 표시하지 않는다. 비교 기준은 실제 내보낸 파일명과 프레임 ID다.

검사 화면의 **Figma에서 이 요소 보기**는 해당 파일의 실행 중인 플러그인으로 검사한 노드 ID를 전달한다. 앱에서 실제 선택·확대가 끝난 확인 응답을 받아 표시한다. 오래된 시안의 플러그인 연결이 끊겼으면 파일에서 다시 플러그인을 실행하고 프레임을 가져온다. 플러그인 최초 등록은 사용자가 Figma 개발 메뉴에서 `figma-plugin/manifest.json`을 고른다.

실제 요소 이벤트는 실행 폴더의 `inspections.jsonl`에 기록한다. SSE는 시작 시 최신 기록을 보내고 실제 추가 이벤트를 전달한다. 화면 크기·측정 단계·스크롤 캡처가 같은 기록만 묶으며, 시안 비교나 버튼 검사를 하지 않은 크기는 미측정으로 표시한다. 검증 결과: `eval/ux-elements-20261014/README.md`.


### 문제와 수정 우선순위

결과 화면은 도구의 심각도와 검사 종류에 따라 문제를 정렬한다. 같은 심각도에서는 동작 문제를 먼저 보여 주며, 단위가 다른 측정값으로 임의 점수를 만들지 않는다. 기본은 전체 화면 하이라이트이고, 목록·시안·구현의 대응 번호를 맞춘다. 부분 확대는 선택할 때만 사용한다. 수정 요청 복사를 먼저 제공하고 Dify 문제 설명과 검색 근거는 펼쳐 볼 수 있다. 검증과 레퍼런스: `eval/ux-priority-20261014/README.md`.


### Dify RAG v6 (2026-10-14)

기존 Dify 지식베이스를 유지하고 현재 구현된 24개 규칙·검사 방법·검증 사례를 구조화했다. 웹 검사는 LLM 설명을 꺼도 Dify에서 검사 방법을 검색하고, 실제 CSS 미디어 경계와 다른 폭의 버튼을 제한적으로 추가 측정한다. 결함별 검색·메타데이터 필터·하이브리드 순위와 적용 조건 재정렬도 Dify 노드 안에서 실행한다. 원래 로컬 코드는 수정하지 않고 첫 검사에서 만든 빌드 사본을 재사용한다.

임베딩 실제 응답과 필요한 검사 근거가 없으면 불완전으로 표시한다. 검사 근거는 결함별로 나눠 숫자·인용을 검증한다. 자세한 구성·적재·제한은 `dify/rag/README.md`, 전후 검증은 `../eval/rag-20261014/`에 있다.


## Dify를 통한 코드 수정과 전체 화면 전후 비교

웹 검사에서 **검사부터 코드 수정·재검증까지 진행(Dify)**을 선택하거나, 완료된 검사에서 **코드 수정·재검증**을 누른다. 검사와 수정은 각각 게시된 Dify 워크플로를 실행한다. Dify 연결 실패 시 로컬 수정으로 우회하지 않는다.

1. 수정 전 소스 사본을 빌드하고 기준 화면과 버튼을 다시 측정한다. 기존 결함이 재현되지 않으면 새 검사를 요청한다.
2. 시안 값·CSS 규칙으로 수정안을 만든다. 실제로 측정한 조상 컨테이너의 간격도 후보에 포함한다.
3. 규칙 수정이 실패하거나 동작 결함이면 로컬 코드 에이전트가 소스를 읽고 검색하고 수정한다. 시안 목적지 문구를 실제 소스에서 검색하며, 존재하지 않는 HTML 목적지는 거부한다.
4. 각 수정안과 전체 수정 묶음을 다시 빌드하고 모든 원래 화면 크기, 추가 검사 크기, 버튼 검사 크기를 재검증한다. 새 결함·악화·새 실패 크기·검사 누락·요소 삭제·시안 대응 감소를 거부한다.
5. 수정 화면에서 Figma / 수정 전 / 수정 후 전체 캡처를 비교하고, 문제별로 선택해 실제 위치를 검은 테두리로 확인한다. 버튼을 누른 뒤 도착한 화면도 비교할 수 있다. 같은 스크롤 위치가 없으면 캡처 없음으로 표시한다.

실행 폴더의 `fix/`에는 `pipeline.json`(별도 Dify 실행 ID), `fixes.json`(시도·피드백·선택 결과), `comparison.json`(전후 비교·범위), `before-defects.json`, `after-defects.json`, `source/`(검증된 변경 파일), `fix_all.patch`가 남는다. 수정 후 미검출을 측정한 0px로 표시하지 않는다.

원본 작업 폴더 적용·되돌리기·PR 올리기는 기존 사람 확인 문구를 유지한다. 수정은 사본에서 수행하며 모든 자동 시도가 성공한다는 보장은 없다. 미해결·상한으로 미시도한 항목은 남은 문제에 표시한다. 프레임 연결과 레시피로 지정한 화면 범위에 대한 검증이며 실기기나 지정하지 않은 화면, 백엔드 업무 로직 전체의 검증은 아니다.
