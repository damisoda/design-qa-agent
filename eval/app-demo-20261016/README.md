# Atelier — 앱 전체 검수·수정 데모

실제 Figma 4개 프레임과 일부러 다른 로컬 앱을 검사하고, 공통 Action 스타일을 수정한 사본을 검증한다. 확인되지 않은 수정은 사용자 원본에 넣지 않는다.

## 시작하기

1. Docker의 기존 Dify와 Mac mini가 실행 중인지 확인한다.
2. 이 폴더의 `Atelier-demo.command`를 더블클릭한다. 터널·중계기를 확인하고 dqa 서버를 연다.
3. <http://127.0.0.1:8792/demo?app=atelier>에서 저장된 실제 결과를 바로 시연하거나 **새 검사부터 자동 수정**을 누른다.

5분 발표에서는 발표 전에 한 번 완료한 실제 기록을 보여주고, 실시간 실행은 별도 시연으로 권장한다. 새 실행은 몇 분 걸린다. 실시간 진행 기록과 모델 재계획이 표시된다. 결과를 미리 성공으로 표시하거나 예제 패치를 답으로 제공하지 않는다. 실패하면 미해결 상태와 실행 기록을 남긴다.

## 발표할 때 보여줄 순서

1. **Figma 시안 열기**: 4개 화면과 Action 컴포넌트의 Primary·Return 변형을 보여준다. 앞 3개 버튼은 파랑, 완료 화면은 다른 의도의 장미색이다.
2. **수정 전 앱**: Explore exhibition → Reserve a visit → Confirm reservation 순서로 누른다. 실제 페이지 이동과 예약 상태가 있는 작은 프런트 앱이다. 로그인·결제·실서비스 백엔드는 없다.
3. **공통 작업**: 화면별 색상 결함 3건이 동일한 CSS 변경 후보 1개로 묶이는 것을 보여준다. 같은 클래스라는 이유만으로 묶지 않고, 바꿀 파일·코드·기대값까지 같은지 비교한다.
4. **거부된 수정**: 전체 `.action` 색을 바꾸면 3개 화면은 고쳐지지만 완료 화면에 D2 회귀가 생긴다. 실제 Chrome 재측정이 이 후보를 거부한다.
5. **모델 재계획**: Gemma가 측정 결과, Figma 계약, 실제 클래스 사용처를 보고 수정 범위를 선택한다. 범위 수정 도구는 관측된 클래스 조합에만 CSS를 추가한다. 채택 여부는 모델이 아니라 재측정기로 정한다.
6. **수정 후 앱과 전체 전후 비교**: 화면 선택에서 4개 화면을 각각 보여준다. 완료 화면의 원래 색과 예약 이동이 유지되는지 직접 누른다. 상세 비교는 흑백 외곽선으로 요소를 표시하며 화면에 색을 덮지 않는다.
7. **Dify 실행 근거**: 검사와 수정 각각의 실제 workflow run ID, 회귀검증 기록, 생성된 patch를 펼친다.

## 검증 경로

```text
데모 버튼 → Dify 검사 워크플로 → 실제 Chrome 측정
          → Dify RAG의 검사 근거 → 추가 크기·버튼 검사
          → Dify 보고서 → Dify 수정 워크플로
          → 공통 원인 후보 묶기 → 규칙 후보 시험
          → 실패 근거 → Gemma 재계획·코드 도구 선택
          → 전체 화면 재측정 → 묶음 수정 재검증
          → 검증된 별도 앱 사본 → 독립 예약 경로 E2E
```

레이아웃 규칙은 모바일 5크기에서, Figma 값 비교는 실제 시안 크기 375×812 및 크기 방식 확인용 보조 폭에서 수행한다. 버튼은 기본 폭과 Dify RAG가 고른 최소·최대 폭에서 누른다. 시안이 없는 크기에 정확한 Figma 배치가 있다고 주장하지 않는다.

독립 E2E 재실행:

```sh
node dqa/demo/verify.js <실제 실행 ID>
```

검증기는 실제 Dify 완료, 회귀가 발생한 거부 기록, 모델의 재계획, 채택된 모델 수정, 원본 파일 해시 보존을 확인한 다음 5크기에서 예약 경로 4단계를 직접 누른다. 결과는 `e2e-result.json`, 캡처는 `evidence/<실행 ID>/`에 저장한다.

## 파일과 한계

- `frontend/`: 의도적으로 틀린 원본. 반복 시연을 위해 보존한다.
- `designs/`: Figma MCP에서 실제 노드를 읽어 내보낸 JSON과 실제 Figma PNG.
- `app-manifest.json`: 화면·프레임·공통 컴포넌트 목록.
- `previews/<실행 ID>/`: 검증된 수정 사본. 원본 적용 확인 문구를 우회하지 않는다.
- `dqa/runs/<실행 ID>/fix/app-plan.json`: 후보, 재계획, 회귀 결과의 체크포인트.
- `dqa/runs/<실행 ID>/fix/comparison.json`: 전체 화면·크기 전후 증거.

이 사례는 개발용으로 만든 통제된 검증 사례다. 한 앱의 성공을 일반 앱 자동 수정 성공률로 해석하면 안 된다. 화면 등록·진입 레시피·Figma 연결은 현재 사람이 제공한다. 로그인 역할, 백엔드 데이터 상태, 모든 포커스/눌림 상태, 실기기 문제, 임의 JS 변경의 기능 안전성은 별도 검증 대상이다. 중단된 작업의 결과는 보존되지만, 모델 대화를 복원해 정확히 중간 단계부터 이어가는 기능은 아직 없다.
