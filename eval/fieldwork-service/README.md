# Fieldwork — 실제 Figma와 서비스 프런트의 검수·수정 데모

5개 화면을 가진 체험 예약 서비스다. 독립 스튜디오의 상품을 검색하고 날짜·시간·인원을 선택한 뒤, 장바구니·쿠폰·예약자 입력·예약 조회·취소까지 이어진다. 실제 결제 서버나 고객 정보는 사용하지 않는다. 단순한 정적 전후 이미지가 아니라 각 화면의 버튼과 상태가 동작하는 로컬 앱이다.

## 열기

`Fieldwork-demo.command`를 더블클릭한다. 기존 Dify Docker와 Mac mini 연결이 필요하며, 스크립트는 `dqa up`으로 터널과 로컬 중계기를 확인한다.

- 시연: http://127.0.0.1:8792/demo?app=fieldwork
- 실제 Figma: https://www.figma.com/design/Yz8NzeU2wjqmzuYkRvvSfm?node-id=5-6
- 작은 Atelier 비교 예제: http://127.0.0.1:8792/demo?app=atelier

Figma는 기존 파일의 **Fieldwork · service** 페이지에 있다. 이전 Atelier 페이지는 보존했다. MCP 쓰기 도구의 호출 오류와 Starter 파일 수 제한 때문에 Figma 앱의 로컬 개발 플러그인으로 편집 가능한 노드·컴포넌트·변수·프로토타입을 만들었다. 실제 Figma 노드 값과 PNG를 다시 내보내 검사에 사용했다. `designs/`의 source는 `figma-plugin`이다.

## 발표 순서

1. **Figma 시안 열기**에서 5개 프레임을 보인다. 검색 → 상품 상세 → 장바구니 → 예약자 입력 → 예약 내역이 한 앱의 흐름임을 설명한다.
2. **수정 전 앱**에서 product를 선택한다. 긴 상품명과 작은 인원 버튼, 녹색이어야 하는 주요 행동 버튼을 보여준다.
3. **새 검사부터 자동 수정**을 누르거나 완료된 실제 기록을 보여준다. 실시간 실행은 전체 화면과 사용자 흐름을 반복 측정하므로 수분 이상 걸린다. 발표 시간에는 완료된 기록을 먼저 준비한다.
4. **실제 진행 기록**과 **에이전트가 무엇을 바꿨나요?**에서 공통 수정 후보, 거부된 후보, 모델 재계획을 확인한다. 정상 취소 버튼의 색까지 바꾸는 전역 수정은 회귀검증에서 거부되어야 한다.
5. **수정 후 앱**에서 상품 → 장바구니 → 쿠폰 `WEEKEND10` → 예약자 입력 → 예약 완료까지 눌러본다. 테스트 정보는 Jamie Park / jamie@example.test / 01012345678을 쓴다. 약관 체크는 데모 내부 상태이며 실제 결제·계약을 제출하지 않는다.
6. bookings에서 **Cancel booking → Keep booking**과 **Yes, cancel visit**을 각각 보여준다. 수정 전후 앱은 별도 상태를 사용한다.
7. **전체 검사·전후 비교**에서 전체 화면의 검은 번호 윤곽선, CSS 패치, 실제 Dify 검사/수정 workflow run ID를 보인다.

## 평가 구성

| 항목 | 내용 |
|---|---|
| 실제 화면 | Catalog 5:32, Experience details 5:148, Your bag 5:206, Checkout 5:265, My bookings 5:313 |
| 정상 기준본 | `reference/` — Figma 비교 0건을 확인한 뒤 고정 |
| 의도적 결함 구현 | `frontend/` — 주요 버튼 색상 override 누락, 긴 상품명 nowrap, 수량 버튼 18px |
| 독립 정답 기록 | `fault-manifest.json` — 에이전트 입력/수정 폴더 밖에 보관 |
| 기능 검증 | `journey.js` — 15개 확인 × 5개 모바일 크기 |
| 후보별 회귀 | 신뢰된 dqa recipe의 booking-lifecycle — 최소/최대 폭에서 실제 클릭·금액·폼·취소 확인 |
| 최종 독립 검증 | `verify-repair.js <run_id>` — Dify 필수 경유, 실제 재계획, 원본 해시, 모든 화면 스타일과 기능 검사 |

초기 사용자 흐름이 이미 실패하면 중간 후보는 실패 지점을 앞당기거나 정상 흐름을 깨뜨릴 수 없다. 최종 완료는 모든 사용자 흐름이 통과해야 한다. 후보 검증을 통과한 공통 수정이 다른 파생 문제도 해결하면 중복 수정을 생략하고 최종 묶음 검증으로 확인한다.

원본 자동 적용은 하지 않는다. 검증된 수정 사본만 `previews/<run_id>/`로 만든다. 적용·되돌리기·PR 게시의 사람 확인 문구는 에이전트가 채우지 않는다.

## 한계

등록된 화면과 명시한 사용자 흐름의 검증이다. 로그인 권한, 실제 결제·백엔드 동시성, 모든 날짜·상품 조합, 실기기 키보드·안전영역까지 검증했다는 뜻은 아니다. 이 앱에 넣은 결함으로 개발했으므로 일반 서비스에 대한 탐지율 수치로 해석하지 않는다. 전체 코드의 임의 기능을 자유롭게 수정하는 범용 에이전트도 아니다. 측정·시안 계약·허용된 수정 도구와 실제 재검증으로 범위를 제한한다.
